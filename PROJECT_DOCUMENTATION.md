# Архитектурное описание проекта

### 1. Общий обзор системы (High-Level Overview)

Проект `tradingAI` представляет собой многофункционального Telegram-бота, предназначенного для автоматизации трейдинга, сбора аналитики, обработки торговых сигналов с помощью ИИ и управления криптовалютными активами. Бот ориентирован на персональное использование (доступ ограничен владельцем) и включает в себя интеграции с биржами (Bybit), блокчейном (TON), а также функции автоматического постинга и парсинга Telegram-каналов.

**Технологический стек:**
- **Основной язык:** JavaScript / Node.js (ECMAScript Modules).
- **Фреймворк для Telegram-бота:** `grammy`.
- **Веб-сервер:** `express` (для обработки вебхуков и Telegram Web App).
- **База данных:** Supabase (PostgreSQL) через `@supabase/supabase-js`.
- **Взаимодействие с API / Блокчейном:** `bybit-api` для Bybit, `@ton/core` для TON, `telegram` (GramJS) для прямого взаимодействия с Telegram MTProto API.
- **Оркестрация ИИ-агентов:** Вспомогательные Python-скрипты, запускаемые из Node.js через `child_process.spawn`.

**Общая архитектурная структура:**
Проект использует **модульную слоистую архитектуру** (Layered Architecture):
1. **Presentation Layer (Слой представления):** Компоненты взаимодействия с Telegram (файлы в `src/composers/`).
2. **Business Logic Layer (Слой бизнес-логики):** Сервисы, инкапсулирующие логику приложения (файлы в `src/services/`).
3. **Data Access Layer (Слой работы с данными):** Модули для связи с Supabase и внешними API (Bybit, Telegram MTProto).
4. **Agent Orchestration (Оркестрация агентов):** Отдельный подкомпонент (`agents_orchestrator.mjs`) для управления специализированными ИИ-навыками, написанными на Python (скрейпинг, финансовый анализ, оптимизация SQL).

### 2. Анализ структуры и связей методов (Method Call Graph & Dependencies)

#### Точки входа (Entry Points):
- `index.mjs`: Основная точка запуска бота. Инициализирует Express-сервер, поднимает бота (`bot.start()` или вебхуки) и запускает фоновый воркер для сбора данных (`startResearchWorker`).
- `agents_orchestrator.mjs`: Отдельный CLI-скрипт или сервис для запуска ИИ-агентов, тестирования навыков (через функцию `runSmoke`) и исполнения Python-скриптов.

#### Критические цепочки вызовов (Core Workflows):

1. **Обработка команд пользователя (User Interaction Workflow):**
   - **Вызов:** Пользователь отправляет команду (например, `/start`).
   - **Маршрут:** `index.mjs` -> `src/bot.mjs` (глобальный middleware проверяет `OWNER_ID`) -> `mainMenuComposer` / `assetsComposer`.
   - **Исполнение:** Композер вызывает соответствующий сервис (например, `bybitService.mjs` для получения баланса) и возвращает отформатированный ответ пользователю.

2. **Фоновый сбор и анализ информации (Research Pipeline Workflow):**
   - **Вызов:** В `index.mjs` вызывается `startResearchWorker()`.
   - **Маршрут:** Запускается таймер, периодически вызывающий `executeResearchPipeline()` из `src/services/researchPipelineService.mjs`.
   - **Исполнение:** `ResearchPipelineService` вызывает `TelegramScraperService` для парсинга постов -> фильтрует их по ключевым словам -> передает в `AIService` для суммаризации (вызов LLM) -> сохраняет результаты в кэш через `ResearchCacheService`.

3. **Telegram MTProto Авторизация и Автопостинг:**
   - **Маршрут:** `autopostingComposer` -> `telegramSessionService.mjs` (`startLogin`, `verifyLogin`).
   - **Исполнение:** Сервис взаимодействует с `TelegramClientManager` для работы с GramJS, отправки кода и сохранения сессии, при этом используя `utils/encryption.mjs` для шифрования конфиденциальных данных.

#### Связанность и зависимости (Coupling & Dependencies):
- **Высокая зацепленность (High Coupling):** Композеры плотно привязаны к конкретным сервисам (например, UI-логика в `assets.mjs` зависит от контрактов `bybitService.mjs` и `tonService.mjs`). Сервисы напрямую импортируют другие сервисы (например, пайплайны жестко связаны с кэшированием и парсингом).
- **Изолированность (Low Coupling):** Утилиты (`src/utils/`) и некоторые классы внутри ИИ-оркестратора относительно независимы. Навыки (Skills) из `skills_agents` полностью изолированы, так как это внешние Python-скрипты, взаимодействующие через stdin/stdout (паттерн **Message Passing / IPC**).

### 3. Подробное описание ключевых модулей/компонентов

#### `index.mjs` & `src/bot.mjs`
- **Ответственность:** Запуск приложения, инициализация графа зависимостей для бота, настройка маршрутизации Express и Telegram-хуков. `bot.mjs` содержит костяк бота, применяет Session Middleware и проверку прав доступа (`OWNER_ID`).

#### `agents_orchestrator.mjs`
- **Ответственность:** Загрузка, конфигурация и запуск агентов и "навыков" (tools), базирующихся на Python (финансовый анализ, скрейпинг, SMM-метрики).
- **Ключевые методы:**
  - `runPython(args, options)`: Обертка над `spawn` для выполнения Python-скриптов и чтения JSON из stdout.
  - `buildTools(skills)`: Фабричный метод, собирающий массив инструментов (Tools) для передачи агентам.
  - `runSmoke(orchestrator)`: Тестовый прогон всех инструментов.

#### `src/services/researchPipelineService.mjs`
- **Ответственность:** Координация процесса сбора новостей, фильтрации и ИИ-анализа.
- **Ключевые методы:**
  - `executeResearchPipeline(options)`: Главный метод пайплайна. Собирает посты, фильтрует по ключевым словам (паттерн **Filter**), агрегирует через ИИ и пишет в базу.
  - `startResearchWorker(options)`: Запуск цикличного процесса сбора (паттерн **Worker/Scheduler**).

#### `src/services/telegramSessionService.mjs`
- **Ответственность:** Управление "пользовательскими" (MTProto) сессиями Telegram для задач, недоступных через Bot API (чтение чужих каналов, автопостинг).
- **Ключевые методы:**
  - `startLogin({ telegramId, phoneNumber })`: Инициирует отправку кода подтверждения.
  - `verifyLogin({ telegramId, code, password })`: Завершает вход и сохраняет зашифрованную сессию (паттерн **Facade** над GramJS).
  - `fetchRecentChannelPosts()`: Получение истории сообщений канала.

#### Крупные сервисы интеграции (`bybitService.mjs`, `aiService.mjs`, `walletIntelService.mjs`)
- **Ответственность:** Общение с внешними провайдерами данных.
- **`aiService.mjs`**: Инкапсулирует логику промптинга, обращений к LLM (OpenAI/Anthropic и др.) и парсинг ответов (включает паттерны **Adapter** и **Strategy** для различных провайдеров, если применимо).
- **`bybitService.mjs`**: Работа с балансами, выставление ордеров, получение метрик (использует `bybit-api`).

### 4. Потенциальные проблемы и рекомендации (Refactoring & Risks)

1. **Проблема God-классов и разрастания сервисов:**
   - **Описание:** Некоторые файлы в папке `services/` (например, `bybitService.mjs`, `aiService.mjs`, `autopostingService.mjs`) имеют слишком большой размер (от 18 до 26 KB). Они берут на себя слишком много обязанностей (нарушение SRP).
   - **Рекомендация:** Провести рефакторинг, разбив крупные сервисы на более мелкие домены (например, `aiService.mjs` разделить на `aiPromptBuilder`, `aiClient`, `aiResponseParser`).

2. **Неявная зависимость от Python-окружения (Environment Coupling):**
   - **Описание:** `agents_orchestrator.mjs` вызывает Python-скрипты через консоль. Это создает хрупкую систему: ошибки в Python-библиотеках, проблемы с кодировкой в stdout, отсутствие нужной версии интерпретатора могут незаметно "уронить" пайплайн.
   - **Рекомендация:** Использовать микросервисную архитектуру. Обернуть Python-скрипты в легковесный HTTP-сервер (например, с использованием FastAPI) и обращаться к ним из Node.js через REST API (или gRPC).

3. **Узкое место в State Management для MTProto:**
   - **Описание:** В `telegramSessionService.mjs` состояние и сессии сохраняются локально в JSON-файл (`data/telegram-mtproto-session.enc.json`). В случае развертывания бота в облаке (Serverless, Docker-контейнеры без Persistent Volumes), данные авторизации будут потеряны при перезапуске.
   - **Рекомендация:** Перенести хранение сессий и конфигурации авторизации в базу данных (Supabase), которая уже интегрирована в проект.

4. **Масштабируемость и Hardcoded ограничения:**
   - **Описание:** В проекте используется проверка на единственного владельца (`OWNER_ID`). Логика обработки сессий во многом неявно полагается на то, что активный пользователь всегда один.
   - **Рекомендация:** Если планируется масштабирование на нескольких пользователей (даже узкий круг доверенных лиц), потребуется переработать систему ролей, хранения пользовательских ключей API бирж (убедившись в их надежном шифровании в БД) и изоляцию контекста в композиторах.
